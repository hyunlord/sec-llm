# 하드웨어 운영 노트 — DGX Spark (GB10 Grace-Blackwell)

이 문서는 **이 장비에 한정된 운영상의 발견**을 모은다. 코드에서 읽어낼 수 없고,
한 번 당해봐야 알게 되는 종류의 것들이다. 새로 합류한 사람이 같은 실수를
반복하지 않도록 사건과 그로부터 채택한 규칙을 함께 적는다.

---

## 규칙 (모든 작업지시서에 적용)

아래 네 가지는 이 장비에서 작업하는 모든 단계에 적용된다. 이 문서 하나만 읽어도
규칙이 전달되도록 여기에 다시 적어 둔다.

1. **학습 호스트에서 소스 컴파일 금지.**
   빌드를 유발하는 `pip install` 금지, `setup.py build_ext` 금지, `nvcc` 직접 호출 금지.
   **휠(wheel)만 쓴다.** 어떤 패키지에 이 플랫폼용 휠이 없다면, **그 부재 자체가 발견 사항**이다.
   기록하고 넘어간다. 빌드해서 뚫으려 하지 않는다.

2. **모든 서브프로세스는 하드 메모리 상한 아래에서 돈다.**
   가능하면 `systemd-run --scope -p MemoryMax=32G -p MemorySwapMax=0`,
   불가능하면 `ulimit -v`. **OOM killer가 해당 작업을 죽여야지, 호스트를 죽이면 안 된다.**
   `MemorySwapMax=0`이 핵심이다. RSS만 제한하면 스왑 스래싱으로 여전히 장비가 멎는다.

3. **백그라운드 작업 금지.**
   모든 것은 오케스트레이터의 포그라운드에서 돈다. `nohup`은 오케스트레이터 자신에게만 허용된다.

4. **프로세스를 죽이는 감시자(watcher) 금지.**
   SSH로 들어와 패턴 매칭으로 프로세스를 죽이는 백그라운드 스크립트는 안전장치가 아니다.
   그런 스크립트가 커밋되어 있다면 삭제한다.

## 사건 1 — 병렬 소스 빌드가 장비 전체를 내렸다 (2026-09-18)

### 무슨 일이 있었나

Gate 0 준비 중, 실패 모드 (2)(`flash-attn`의 sm_121 커널 부재)에 대한 증거를 모을
목적으로 `flash-attn==2.8.3.post1`을 소스에서 빌드하려 했다.

```bash
MAX_JOBS=16 FLASH_ATTENTION_FORCE_BUILD=TRUE \
  uv pip install --no-build-isolation "flash-attn==2.8.3.post1"
```

빌드 시작 약 2분 뒤 호스트가 SSH와 ICMP 양쪽에 응답하지 않게 되었다. Tailscale 상에서도
노드가 offline으로 표시되었다. **1시간 이상 자체 복구되지 않았고 물리적 전원 재투입이
필요했다.** 그 시점까지 완료된 체크 결과는 하나도 없었다.

### 왜 그런가 — 통합 메모리(unified memory)

GB10 Grace-Blackwell에서 **호스트 RAM과 GPU 메모리는 물리적으로 같은 풀**이다
(이 장비 기준 128GB). 이것이 일반적인 x86 + 별도 GPU 서버와 결정적으로 다른 점이다.

| | x86 + 개별 GPU | GB10 통합 메모리 |
|---|---|---|
| 호스트 컴파일이 GPU 메모리를 잡아먹나 | 아니오 | **예 — 같은 풀이다** |
| 호스트 RAM 고갈의 영향 범위 | 해당 프로세스 (+스왑) | **GPU 작업 포함 장비 전체** |
| CUDA allocator 상한으로 막히나 | 해당 없음 | **아니오 — 컴파일러는 CUDA로 할당하지 않는다** |

`nvcc` 작업 하나가 수 GB의 호스트 RSS를 쓴다. `MAX_JOBS=16`이면 그 16배가 동시에
올라오고, 여기에 이미 쓰이고 있던 약 28GB가 더해지면서 풀이 고갈됐다. 커널은 OOM
killer를 부르는 대신 스왑 스래싱에 들어갔고, 그 상태에서는 sshd와 tailscaled조차
스케줄링을 받지 못한다.

### 오해하기 쉬운 지점 — 두 상한은 다른 것을 막는다

`torch.cuda.set_per_process_memory_fraction()`을 걸어 두는 것은 의미가 있지만,
**이 사건을 막지 못한다.** 두 상한의 역할을 섞어서 이해하면 안 된다.

| 상한 | 무엇을 막나 | 이 사건을 막았나 |
|---|---|---|
| `torch.cuda.set_per_process_memory_fraction` | **CUDA allocator**의 디바이스 할당. 과도한 학습 설정이 깔끔하게 `OutOfMemoryError`를 내도록 해서 단계적 하향 사다리가 작동하게 한다 | **아니오.** 컴파일러는 CUDA를 거치지 않는다 |
| `systemd-run --scope -p MemoryMax=… -p MemorySwapMax=0` | **호스트 RSS**. cgroup 안에서 OOM killer가 먼저 발동한다 | 예 — 다만 근본 해법은 애초에 컴파일하지 않는 것 |

체크 07에는 두 상한이 모두 적용되어 있다. CUDA 쪽은 스크립트 안에서,
호스트 쪽은 `scripts/env_check/_limits.py`가 오케스트레이터에서 감싸 준다.

### 채택한 규칙

위 규칙 1과 2. 그리고 실무적으로 한 줄 더:

> **코어 수에 비례해 확장되는 모든 작업**(빌드, 인덱싱, 병렬 데이터 처리, `-j$(nproc)`류)은
> 이 장비에서 **명시적 메모리 상한 없이 실행하지 않는다.**

## 운영상 권고 — 아직 처리되지 않음

### LAN 고정 주소 + sshd

현재 이 장비에 접근하는 경로는 **Tailscale 하나뿐**이다. 장비가 멎으면
tailscaled도 함께 멎기 때문에, 모든 행(hang)이 물리적 접근을 요구한다.
사건 1에서 1시간 이상을 날린 직접적인 이유가 이것이다.

권고: LAN 고정 IP를 부여하고 그 인터페이스에서도 sshd가 listen하도록 구성한다.
같은 네트워크 안에 있는 한 다음 행에서는 물리적 접근 없이 들어갈 수 있다.
(이 작업은 Gate 0 범위 밖이며, 별도로 수행해야 한다.)

### 게이트 실행 전 청결 확인

게이트를 돌리기 전에 항상 확인한다. 살아남은 빌드 프로세스가 있다면 그 자체가 발견 사항이다 — 기록한 뒤 종료시킨다.

```bash
uptime
free -g
nvidia-smi
ps aux --sort=-%mem | head -20
```

## 장비 제원 (체크 01이 매 실행마다 갱신)

정확한 최신 값은 `env/gate0.json`의 체크 01 결과와 `reports/env-report.md`를 본다.
아래는 방향을 잡기 위한 대략치다.

- `aarch64`, NVIDIA GB10, 컴퓨트 능력 `sm_121`
- 통합 메모리 약 119 GiB (호스트와 GPU가 공유)
- CUDA 런타임 13.0, 드라이버 580.x
- Docker `linux/arm64` 사용 가능
- torch는 **반드시** PyTorch `cu130` 휠 인덱스에서 설치 (`UV_TORCH_BACKEND=cu130`).
  PyPI 기본 인덱스는 CUDA 12 빌드를 준다 — 실패 모드 (1).
